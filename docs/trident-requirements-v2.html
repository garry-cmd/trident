1. Vision

Trident is a Raspberry Pi–based marine instrumentation platform that replaces an iPad/Navionics chartplotter, the Vesper WatchMate AIS app, and Victron Bluetooth monitoring with a single, always-on system accessible from any device on the boat's WiFi.

The immediate goal is to build Trident for a single boat — the builder's — and cruise to Mexico with it. The long-term vision is that Trident becomes the hardware companion to Keeply.boats: any Trident installation feeds instrument-grade voyage data into Keeply's logbook automatically, creating a level of automated logging that manual-entry apps can never match. That positions Keeply uniquely in the cruising software market.

The path from personal build to commercial product is real but distant. Build for one boat first. Get it right. The product opportunity follows from the data pipeline, not the other way around.

2. Problems to Solve

Problem 1

iPad/Navionics Power Drain

iPad running Navionics as primary chartplotter drew power faster than it could charge, leaving no iPad for other use.

Fix: Pi as always-on 12V appliance, display decoupled
Problem 2

WatchMate App Unreliable

Vesper WatchMate lacked robust CPA/TCPA alerting, configurable guard zones, and escalating alarm severity. Warnings inadequate for offshore.

Fix: Trident AIS watch with proper alerting + physical alarm
Problem 3

AIS WiFi Saturates at 2 Devices

XB-8000's 10mW 802.11b/g AP choked when a second device connected. AIS targets visibly disappeared.

Fix: Pi as sole data consumer via N2K, fans out to unlimited clients
Problem 4

Starlink Kills AIS WiFi

Devices can only sit on one WiFi network. Firing up Starlink for weather meant dropping AIS data.

Fix: Single boat LAN with Starlink as WAN uplink
Problem 5

Victron Bluetooth Contention

Battery/solar monitoring requires Victron app over Bluetooth, which fights with BT speaker and only supports one connection.

Fix: Cerbo GX puts Victron data on N2K + LAN
Problem 6

No True Battery SOC

The BMV-712 (coulomb counter) is purchased but not installed. SOC guessed from voltage — unreliable.

Fix: Install BMV-712, wire to Cerbo via VE.Direct

3. Design Principles

Every device does one job. The XB-8000 is a sensor, not a data server. The router routes. The Pi concentrates data. Overloading a device with infrastructure duties is the root cause of every problem above.

Wired over wireless for critical data paths. N2K backbone and USB carry instrument and AIS data. WiFi is for consumption, never for infrastructure transport.

Internet is an uplink, not a network. Starlink feeds the router's WAN port. The boat LAN stays up whether the dish is powered or not. All navigation, AIS, and power data works fully offline.

Display is decoupled from compute. The Pi runs headless at 3–5W. Crew use their own devices (iPad, phone, laptop) as displays via the browser.

Don't build what's already built. OpenCPN handles passage planning on a laptop. Signal K concentrates data. The custom build is the web-based chart view, AIS alerting, dashboard, and Keeply data pipeline — the parts where existing software fails.

Physical alarm is the safety floor. Push notifications depend on internet, PWA state, and phone OS behavior. The GPIO-driven horn depends on 12V power and a relay. The horn is the wake-the-boat alarm. Everything else is convenience layered on top.

7. Software Stack

Base OS & Data Layer

OpenPlotter (Raspberry Pi OS + marine packages)

Pre-configured Pi distribution bundling Signal K, OpenCPN, and CAN bus drivers. Alternative: clean Pi OS with Signal K installed manually.

Signal K Server

Data backbone. Ingests NMEA 2000 (Actisense NGX-1), Victron MQTT (Cerbo GX). Normalizes into JSON over WebSocket and REST. All Trident views consume Signal K — never talk to hardware directly.

  • N2K plugin: reads Actisense NGX-1 USB gateway
  • Victron Venus plugin: Cerbo GX over MQTT for detailed data
  • Derived data plugin: CPA/TCPA calculation from AIS position reports
  • Anchor alarm plugin (built-in, configurable)

Passage Planning (Desktop)

OpenCPN

Battle-tested chartplotter for route planning, waypoint management, and GRIB weather overlays. Runs on the Pi's HDMI or on a laptop. Not browser-based — serves a different moment than Trident's chart view.

  • Chart sourcing for Mexico: O-Charts Blue Latitude (Sea of Cortez + Pacific Mexico, ~€72 total), SEMAR hydrographic charts, Chart Locker satellite MBTiles for Baja's outer coast

Trident Web Application (Custom Build)

Next.js / React / TypeScript PWA served from the Pi at http://trident.local. Accessible from any browser on the boat's WiFi. Add to home screen for full-screen PWA experience and push notification eligibility on iOS.

Chart View

Real-time navigation chart with AIS overlay. Uses Leaflet or MapLibre GL for pan/zoom/pinch with marine chart tiles (pre-downloaded for offline use). Not a replacement for OpenCPN's passage planning — this is the always-available "where am I and what's around me" view on any device.

  • Pan, pinch-zoom, rotate on touch devices — standard map library behavior
  • AIS targets overlaid with same danger/caution/safe color coding
  • CPA intercept geometry drawn for threat targets
  • Own vessel with heading vector and track trail
  • Auto-recenter on vessel after pan timeout (configurable)
  • Floating instrument bar and target list card overlay
  • Tile source: ENC charts via tile server on Pi, or OpenSeaMap, pre-cached before departure
  • Night mode (red-on-black)

Radar View (Situational Awareness)

Head-up relative-motion display. No cartography — purely spatial. Range rings, guard zone ring, all targets plotted with heading vectors and CPA lines. Full target list in right panel with CPA/TCPA sorted by threat.

  • Range rings (1nm, 2nm, 3nm — adjustable)
  • Configurable guard zone radius per crew profile
  • Escalating color coding: red (<0.5nm CPA), amber (<1nm), green (safe)
  • Target trails, heading vectors, CPA intercept geometry
  • Compact instrument strip at bottom

Dash View (Power & System)

Large KPI cards for battery management and system health. Three sections: system status, battery/power, and solar production.

  • System status row: GPS fix quality (satellites, HDOP, WAAS), AIS transponder state (targets, TX interval, last RX), connected clients (device names/count)
  • Hero SOC card with 12-hour sparkline trend
  • Battery voltage, current flow, time remaining
  • Per-MPPT solar yield, panel voltage, charge state, daily peak
  • 7-day solar harvest bar chart for weather/cloud pattern
  • Net energy balance (solar in vs load out)
  • Consumed today vs yesterday for pattern comparison
  • Autopilot monitoring widget (read-only): heading, mode, set course, rudder angle

Settings View (Per-Crew Notifications)

Every crew member gets their own alert profile with individually configurable thresholds. Profiles are tied to device via cookie — no accounts, no passwords. Crew opens trident.local, enters their name, gets their profile.

  • Per-crew threshold configuration for all alert rules
  • Four severity tiers: Info (visual badge), Warn (push + optional audio), Alarm (push + audio + persistent), Critical (all + physical horn)
  • Two notification toggles per rule: push notification and audio independently
  • AIS alerts: CPA proximity, CPA critical, TCPA urgency, guard zone breach
  • Power alerts: low SOC, critical SOC, low voltage, high current draw, solar underperform
  • Navigation alerts: shallow depth, barometric pressure drop, SOG low (stalled/dragging)
  • Boat-level physical horn thresholds: skipper-only, fires regardless of individual profiles
  • Crew can make their devices more sensitive but cannot disable boat-level alarms

DSC Calling (Pending Hardware Verification)

One-Tap DSC Individual Call

The Standard Horizon GX1850 VHF is on the N2K backbone. Trident adds a CALL button to the target detail card. Tap Call → confirm MMSI → Trident sends PGN 129808 via Signal K → NGX-1 → N2K → GX1850 initiates DSC individual call. If testing reveals the GX1850 doesn't accept the PGN command, the button degrades gracefully to displaying the MMSI in large digits for manual dialing. Verify during Phase 3.

Alert Escalation Architecture

Layered Alert System

All alert logic runs on the Pi server-side. No alert depends on a specific client device being open or awake.

  • Layer 1 — Physical horn (GPIO relay): fires at boat-level critical thresholds. No WiFi, no phone, no internet in the path. Wakes the whole boat.
  • Layer 2 — Active browser audio: any device with Trident open plays audio through its speaker. Reliable on Android; iOS may kill background audio.
  • Layer 3 — Push notifications (PWA): delivered to crew phones via Apple/Google push servers. Requires internet (Starlink up). Nice convenience layer, never the safety-critical path.
  • Layer 4 — Visual badge: always works. The Trident UI shows the alert in the top bar, highlights the target, changes the color coding. If anyone is looking at any screen, they see it.

8. Keeply.boats Integration

Long-term product vision

Trident is the hardware arm of Keeply. The Signal K → Supabase pipeline bridges boat instruments to the Keeply logbook. Build for one boat first; the commercial opportunity follows from proving the data pipeline, not from premature productization.

Voyage Data Sync Service

A background service on the Pi buffers structured voyage data locally (SQLite) and pushes it to Keeply's Supabase backend whenever Starlink is available. The sync is opportunistic and resilient — data accumulates during passages and flushes when internet appears.

  • GPS track (position, SOG, COG) at configurable interval (e.g., every 30 seconds underway)
  • Daily summary: distance run, hours underway, max/avg speed
  • Anchorage detection: arrival/departure times, position, duration
  • Weather conditions: barometric pressure, wind speed/direction, temperature
  • AIS encounter log: notable close approaches (CPA below threshold), vessel names/MMSI
  • Battery/solar patterns: daily consumption, solar harvest, SOC curve
  • Depth profile along track
  • Alert history: what fired, when, what triggered it

Keeply Logbook — Automatic Entries

The cruiser opens Keeply at a cafe in La Paz and their entire passage log is already there, richer than anything they'd write by hand. The logbook gets entries no one had to type.

  • GPS track plotted on a chart for each passage
  • Anchorages with positions, arrival/departure, duration
  • Weather conditions from onboard instruments (not forecast data — actual)
  • Notable AIS encounters: "cargo ship passed at 0.3nm at 02:47"
  • Battery/solar performance over the passage
  • Manual notes added by crew from Trident's UI sync to the same timeline

Future: Open Signal K Integration

The sync doesn't need to be Trident-specific. Any Signal K server can push to Keeply via API. Trident is the most polished path, but the Keeply endpoint accepts data from any source. Potential Keeply premium feature: "Connect your Signal K server for automatic voyage logging." The open-source cruising community would adopt this.

9. Build Phases

Ordered by standalone value. Each phase works on its own. Later phases don't rework earlier ones.

  1. 1

    Install BMV-712

    Wire the shunt to the battery bank's negative lead. Immediate standalone value: true SOC via Bluetooth, even before the Cerbo. No new purchases. Highest impact, lowest effort.

  2. 2

    Peplink Router + Unified WiFi

    Install router, Starlink to WAN port, single boat SSID. Fixes "Starlink kills AIS" immediately. Creates the LAN everything else will use.

  3. 3

    Raspberry Pi + Signal K + Actisense NGX-1

    Set up Pi with OpenPlotter, connect NGX-1 to N2K backbone. Verify Signal K ingests all instruments + AIS. Disable XB-8000 WiFi. Signal K's built-in web UI gives basic instrument display to all devices — no custom code yet.

  4. 4

    Victron Cerbo GX

    Install Cerbo, wire 2 MPPTs + BMV-712 via VE.Direct. Connect to N2K + router Ethernet. Verify Triton 2 shows SOC, Signal K ingests Victron MQTT. Battery and solar data flows through the same system as navigation.

  5. 5

    Physical Alarm System

    Wire Pi GPIO → relay → 12V horn. Write the server-side alert engine that evaluates Signal K data against thresholds and triggers the relay. This is the safety floor — ship it before the pretty UI.

  6. 6

    Trident Web App — Radar + Dash + Settings

    Build the Next.js/React/TypeScript PWA. Radar view with CPA/TCPA. Dash view with KPI cards. Settings with per-crew profiles. Served at trident.local. This is the core custom development effort.

  7. 7

    Trident Chart View

    Add the web-based chart with AIS overlay. Tile server on Pi for offline marine charts. Pre-download chart tiles for cruising grounds before departure. More complex than the other views due to tile infrastructure.

  8. 8

    OpenCPN + Chart Sourcing

    Install OpenCPN on Pi/laptop. Purchase Blue Latitude charts via O-Charts, download SEMAR and Chart Locker tiles. Configure for Mexico passage. The iPad continues as a fallback chartplotter until this is ready.

  9. 9

    Keeply Voyage Sync

    Build the SQLite buffer + Supabase sync service. Define the data model for voyage logs, anchorages, and encounters. Wire into Keeply's logbook. This phase bridges Trident to Keeply and is the foundation of the long-term product vision.

  10. 10

    Autopilot Control (Phase 2 — deferred)

    Add write commands to the tillerpilot via Signal K PUT. Requires safety gates: confirmation dialogs, auto-standby on device disconnect, physical controller always overrides. Only build this if read-only monitoring proves insufficient.

Phasing rationale

Each phase delivers standalone value. Phases 1–4 are hardware installation with proven software. Phase 5 is the safety floor. Phases 6–8 are the custom and open-source UI. Phase 9 bridges to Keeply. Phase 10 is deferred until proven necessary. If the project stalls at any point, what's built so far still works.

10. Offline Behavior

Everything that matters runs on the local network with zero internet. The Pi serves Trident over the LAN. Signal K feeds all data over the LAN. The Peplink keeps WiFi up whether Starlink is powered or not. Chart tiles are pre-cached on the Pi. The physical alarm fires from GPIO.

The one exception: push notifications to a sleeping crew member's locked phone route through Apple/Google push servers, so they require internet. This is why the physical horn is Layer 1 and push notifications are Layer 3. When Starlink is up, push works as a convenience. When it's down, the system doesn't degrade in any safety-critical way.

11. Out of Scope (Explicit)

  • Orion-Tr Smart DC-DC integration (Bluetooth-only hardware; excluded unless replaced with Orion XS)
  • Building a custom chart rendering engine (Leaflet/MapLibre handles map rendering; OpenCPN handles passage planning)
  • Autopilot write commands in Phase 1 (read-only monitoring only; control deferred to Phase 10 with safety gates)
  • Radar integration (not in current instrument set; future N2K addition if radar is added)
  • Remote monitoring from shore (requires always-on internet; future Starlink add-on)
  • Commercial productization of Trident hardware (long-term vision; build for one boat first)
  • Multi-vessel fleet management (Keeply may want this eventually; not in scope for personal build)
